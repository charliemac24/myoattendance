# SMS outbox

## Purpose

Successful QR attendance scans may create durable `sms_messages` rows with `pending` status. This phase never calls Semaphore and does not add a sender worker or cron endpoint.

## Scan flow

`ProcessAttendanceScan` creates the authoritative attendance event first, then `QueueAttendanceSms` evaluates SMS entitlement, resolves the person's `contact_number`, selects the matching enabled organization template, renders the message, and persists the outbox row in the same database transaction. If SMS is not entitled, not configured for the event, or there is no valid phone number, attendance still succeeds and no row is created.

Notification types are `time_in` for `check_in`, `late` for `late_check_in`, and `time_out` for `check_out`. Absence is not generated by scanning. Each legitimate attendance event is independent, including multiple IN/OUT periods.

## Snapshots and idempotency

The row stores the normalized recipient phone, rendered message, sender name, organization, person, attendance event, provider (`semaphore`), and notification type. These values do not change if a person edits their number or a template later changes. A database uniqueness constraint on `attendance_event_id`, `notification_type`, and `recipient_phone` prevents duplicate outbox rows for the same event and recipient.

## Status and worker contract

New rows use `pending` with `attempt_count = 0`. `php artisan sms:process` runs every minute via Laravel's scheduler, claims at most 50 eligible rows by oldest `created_at`/`id`, and calls Semaphore outside the database transaction. Claiming uses a short `lockForUpdate()` transaction and `processing_started_at`; the HTTP request is never made while a row lock is held. `attempt_count` means actual provider attempts and is incremented at claim time immediately before the request. The default retry policy is one minute after attempt 1 and five minutes after attempt 2, with three maximum attempts. HTTP 429 honors `Retry-After` when numeric; timeouts, connection failures, server failures, and malformed successful responses are retryable. Validation, authentication, and explicit provider rejection are permanent failures.

Semaphore `POST /api/v4/messages` is sent as form data using the snapshotted `recipient_phone`, `message`, and `sender_name`; the API key comes only from `config('services.semaphore.api_key')`. A response is accepted only when it is the documented array containing `message_id` and a `queued`, `pending`, or `sent` status. `sent` means Semaphore accepted the request, not handset delivery. The safe response is retained in `provider_response`, with `provider_message_id` and `provider_status` extracted separately.

Super Admins can set an optional sender-name override per organization. New outbox records use that override; blank means `config('services.semaphore.sender_name')` from `SEMAPHORE_SENDER_NAME`. Sender names are limited to 11 alphanumeric characters for Semaphore compatibility. Existing queued rows retain their snapshotted sender name.

Records stuck in `processing` for more than 10 minutes are marked `failed` with `provider_uncertain`. They are not automatically resent because Semaphore may have accepted the request before the worker crashed; review is required before any explicit retry operation. This preserves the known external exactly-once limitation: a local database cannot atomically commit with an external provider.

The scheduler is driven by one production cron entry, for example `* * * * * cd /path/to/application && php artisan schedule:run >> /dev/null 2>&1`. Do not expose an HTTP cron endpoint. Use `php artisan sms:process --limit=1` for a controlled manual test; automated tests always fake HTTP and never use the real key.

For this Docker-based local setup, Artisan commands run directly from macOS use `DB_HOST=127.0.0.1` and `DB_PORT=3307`, the published MySQL port. The Docker `app` service overrides those values back to `DB_HOST=mysql` and `DB_PORT=3306` for container-to-container access.

## Security and tenancy

Organization and person IDs come from trusted attendance context, never scanner input. There is no public endpoint for inserting SMS rows. Semaphore settings are read through `config('services.semaphore')`; the API key is never logged, returned, or stored in provider responses.

The current project has no `PersonContact` model/table, so the existing `persons.contact_number` field is the recipient source. Phone snapshots strip all non-numeric characters, normalize Philippine `09...` numbers to `639...`, and accept other 10–15 digit international values. Stored `recipient_phone` values therefore contain digits only, as expected by Semaphore.
